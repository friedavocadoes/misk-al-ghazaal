## 7. Current Architecture / Onboarding Map (verified from source 2026-10-17)

This section and the corrected entries above supersede historical implementation descriptions. Source inspection does not establish which migrations/settings are applied in a deployed Supabase project.

### Runtime and routes

- Root `src/app/layout.tsx` passes children through. `[locale]/layout.tsx` owns storefront html/body, fonts, NextIntlClientProvider, and Swiper/Leaflet CSS. `/admin/layout.tsx` owns a separate EN html/body and the admin Toaster. Do not move storefront providers into the root without accounting for admin/auth/API routes.
- Canonical storefront: `/`, `/collection/[slug]` (including `all`), `/collections`, `/product/[slug]`, `/search?q=`, `/blog`, `/blog/[slug]`, `/pages/[slug]`, `/private-label`, `/locate-us`, `/cart`, `/checkout`, and `/account/*`. Legacy `/collections/[slug]` and generic `/[slug]` resolve through redirect routes. EN uses clean URLs, AR `/ar/...`.
- `src/proxy.ts` combines next-intl routing with Supabase session-cookie refresh. It bypasses locale routing for admin/auth and excludes API/static paths via matcher. OAuth code rescue rewrites to `/auth/callback`.
- Storefront catalog reads belong in `lib/store.ts`: public cookie-free Supabase client, relational mapping to camelCase domain types, soft-delete/active filtering, ranking/facets. `site.ts` contains client-safe static/localizable copy; `footer.ts`, `shopper.ts`, pricing, and privileged clients stay on the server.
- Supabase clients: `client.ts` browser session; `server.ts` cookie-authenticated/RLS; `public.ts` anonymous catalog/build reads; `service.ts` secret-key privileged access. `keys.ts` supports modern publishable/secret keys and legacy anon/service-role fallbacks. Never expose secret keys.

### Commerce and access

- CartProvider persists `misk-cart-v1` and syncs `profiles.cart`; WishlistProvider persists account wishlist. Sign-out/account-switch boundaries matter. `CartItem.productSlug` becomes `BagLine.slug` at quote/checkout boundaries; do not interchange their shapes.
- `/api/products` resolves minimal product details for client cart UI; `/api/catalog` serves listing batches; `/api/search/suggest` serves live autocomplete (admin scope is staff-gated).
- `POST /api/quote` and `POST /api/checkout` share server-authoritative `quoteBag` in `lib/pricing.ts`. Client shipping estimates use `pricing-client.ts` (AED 26 flat, free from AED 200). Checkout is COD and allows guests; session identity sets order ownership. Coupon redemption, referral rewards, profile/address memory, stock/sales updates, confirmation mail and invoice attachment follow order creation.
- Shopper reads use authenticated RLS plus user_id filters. Guest order adoption is a separate privileged login bootstrap step (`claimGuestOrders`), rather than an email fallback in shopper order queries.
- `getAdminSession()` accepts only `super_admin` and `orders`. Admin layout is a visual shell, not a global authorization guard: pages AND server actions/handlers must check authorization. Catalog/growth/access/email management requires super_admin; order operations and logs support staff. Bin enforces permissions per entity.
- Admin saves use AdminForm/SaveButton, input-less posts use ActionButton; preserve audit logging, relevant storefront revalidation helpers, and Storage cleanup. Navigation groups are Catalog, Access, Growth, Emails, with Orders/Bin/Logs links.
- Email delivery uses `lib/mailer.ts` per-mailbox SMTP (`hello`, `noreply`, `promo`, `orders`), legacy SMTP fallback and optional no-op behavior. Hello template at `/admin/emails/hello`; campaigns at `/admin/promo`; shopper order requests use `/api/order-issue`. Order mail and promotional preferences are separate.
- Invoice access is `/api/orders/[id]/invoice` with owner/staff authorization, optional download and private Storage. PDF generation/attachment helpers are server-only.

### Known implementation limits (observed, not fixed by this documentation pass)

- `ContactExperience` general contact submit only generates a local reference and advances the UI; it does not persist/send a request. This differs from the working account order-issue API.
- Checkout order/items/history/stock/coupon/referral writes are separate operations, not one database transaction; several follow-up write errors are not inspected. Do not describe this workflow as atomic or concurrency-safe.
- `/api/quote` currently accepts body.userId for coupon eligibility rather than deriving it from a verified session; checkout derives its own session owner. Do not treat quote eligibility as an authorization guarantee.
- Pricing currently does not check that a chosen variant belongs to the supplied product, does not reject paused products, and checks stock per line rather than aggregating duplicate variant quantities. These are follow-up hardening concerns, not guarantees provided by the current server repricing.
- Full search is not equivalent to autocomplete: search hydrates variants only (empty collection/notes relations), so lineup facets cannot work as with fully hydrated collection products. Arabic title matching exists in suggestions, not full search.
- Home H1 is only emitted when configured SEO has h1; the historical assertion that every content page always has an H1 is not a verified invariant.
